## Принципы и конкретность

Основная идея пользователя поддерживается рекомендациями: короткое постоянное руководство, ясные цели и ограничения, подробности по мере необходимости. Но одной абстрактной философии недостаточно. Anthropic рекомендует баланс между хрупкими предписаниями каждого шага и слишком общими пожеланиями. Поэтому обязательность тестов, приватность, изоляция и ownership сформулированы проверяемо, а способы реализации оставлены агенту. Это наше применение рекомендации к проекту. [Anthropic: context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents).

OpenAI описывает `AGENTS.md` как постоянное руководство проекта, а скиллы как упаковку повторяемых задач. Для проекта это означает один корневой набор принципов и связанные документы по темам. [OpenAI: AGENTS.md](https://developers.openai.com/codex/guides/agents-md), [OpenAI: skills](https://developers.openai.com/codex/skills).

У скиллов важны ограниченное назначение, понятное условие применения и загрузка подробностей только при необходимости. Эти свойства полезны и для обычных справочников, но сами по себе не требуют создавать новый скилл. [Anthropic: Agent Skills](https://www.anthropic.com/research/equipping-agents-for-the-real-world-with-agent-skills).

## Что означает требование тестов

1. Новое и изменённое исполняемое поведение сопровождается unit-тестами в том же изменении. Это относится к приложению, провайдерам, native adapters и инструментам разработки.
2. Для UI-взаимодействия дополнительно нужны интеграционные тесты пути от действия и состояния интерфейса до сервиса. Native event routing требует соответствующей UI-автоматизации. Скриншоты дополняют автоматические проверки.
3. Проверяются реальные production-компоненты через существующие targets. Подменяются внешние зависимости, а не само проверяемое поведение.
4. Существующий тест можно расширить или использовать, если он действительно проверяет изменённый контракт. Не требуется создавать новый файл ради каждой строки.
5. Ошибки, отмена, admission, сохранение и восстановление покрываются там, где изменение затрагивает эти контракты.
6. Документации нужны проверки согласованности и ссылок. Генерируемые файлы проверяются через генератор и потребляющий контракт. Фиктивные unit-тесты ради числа не требуются.
7. Ограниченный набор запусков не отменяет обязанность написать тесты. Невыполненная обязательная проверка остаётся явно указанным пробелом.

Это политика для новых изменений и затрагиваемого поведения. Она не утверждает, что весь исторический код уже покрыт, и не устанавливает выдуманный показатель 100 процентов строк.

## Сравнение с FluidVoice

В проверенном upstream нет отслеживаемых `AGENTS.md` и `SKILL.md`; contributor guidance сосредоточено в CONTRIBUTING. Сохраняются тот же macOS XCTest target, standalone probes, общие helpers и отдельные baseline/model diagnostics. Его [CI runner](https://github.com/altic-dev/FluidVoice/blob/b6457f14ed2dca563cad69885fd1d4c4c4d4069b/Tests/run_ci_checks.sh#L87) запускает выбранные probes перед Xcode suite и исключает известный flaky Whisper case.

Upstream [CONTRIBUTING](https://github.com/altic-dev/FluidVoice/blob/b6457f14ed2dca563cad69885fd1d4c4c4d4069b/CONTRIBUTING.md#L59) требует сфокусированного PR, воспроизводимых проверок и достоверных результатов, но не формулирует универсальную обязанность unit-тестов для всего нового кода. Запрошенное требование закреплено как собственный принцип Pichi.

Для масштаба инфраструктуры, а не оценки покрытия: на исходной ревизии Pichi в `Tests/` было 637 отслеживаемых файлов, включая 391 Swift-файл и 107 корневых `run_*` скриптов. В проверенном upstream соответственно 279, 178 и 34. Это числа файлов, не тест-кейсов, assertions или процентов покрытия.

## Почему сейчас без новых скиллов и постоянных субагентов

В проекте уже есть исполняемые обёртки для сборки и проверок. Новый скилл, повторяющий их документацию, создал бы вторую копию политики. Универсальные принципы должны действовать независимо от того, выбрал ли агент скилл. Поэтому общая политика находится в AGENTS, а условные детали в двух тематических справочниках.

Отдельный скилл будет оправдан для устойчиво повторяющегося процесса с явными входами, результатом и условиями применения, например подготовки релизной acceptance-сессии. Тогда место совместно используемого скилла будет `.agents/skills/<name>/SKILL.md`; он должен ссылаться на canonical guides, а не копировать их. Сейчас такой дополнительный слой не нужен для результата этого рефакторинга.

Постоянные агенты по каждому провайдеру также не вводились. Сохранён принцип ограниченного независимого делегирования: отдельный worktree у каждого автора, закреплённые входы, один владелец интеграции, независимое ревью итоговой ревизии и очистка. Для этого анализа использованы два read-only агента; они не запускали сборки и не создавали ресурсы.

## Сохранённые ограничения и фактические пробелы

Сохранены изоляция worktrees, read-only upstream, лицензии, минимизация downstream-изменений, существующие extension points, immutable selection, bounded memory, joined cancellation, общие service operations, защита пользовательских данных и очистка только собственных ресурсов. Сохранены брендовые/security границы, String Catalogs, типографика и полный русский алфавит. Signing, frozen bundle, native light/dark evidence, оба мобильных симулятора перед физическим этапом и кадровое доказательство physical runtime вынесены в рабочий процесс без ослабления.

Проверенный [pichi-ci.yml:41](../../.github/workflows/pichi-ci.yml) включает macOS-тесты по условию ручного запуска или repository variable. [Мобильный job:56](../../.github/workflows/pichi-ci.yml) выполняет opt-in simulator build, не runtime-тесты. Значение repository variable и серверные branch rules в этом аудите не запрашивались. Проверенные schemes/workflows не задают обязательный числовой coverage gate. Документы не включают CI и не исправляют покрытие старого кода автоматически.

Следующее отдельное инфраструктурное улучшение при необходимости: измерить исходное покрытие, обеспечить запуск нужных native targets в CI и выбрать проверяемый порог для изменений. До измерения нельзя обещать процент. Перенос старых source-projection probes в XCTest остаётся постепенной работой по затрагиваемым контрактам, а не скрытой частью этого документационного рефакторинга.
