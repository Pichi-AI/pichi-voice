# Рефакторинг по принципу наименьших изменений

Документ фиксирует архитектурный разбор расхождения Pichi Voice с FluidVoice, изменения первого PR рефакторинга и план следующих шагов. Его цель: чтобы каждое следующее обновление из upstream было дешевле, а собственный код был меньше и понятнее, без потери функций.

## Входные данные

| Что | Ревизия |
| --- | --- |
| Наш `main`, на котором построена ветка | `a452e10a` (PR #89, слияние FluidVoice v1.6.13-beta.2) |
| Upstream `main` | `fc59c463` = тег `v1.6.13-beta.2`, целиком входит в наш `main` |
| Снимок, на котором шёл подробный разбор | `10e8a70d` (30 октября, PR #84) |

Подробные отчёты семи подсистем сделаны на `10e8a70d`. Каждый пункт, который изменён в этом PR, перепроверен на `a452e10a`: уникальность якорного текста, поиск ссылок по всему репозиторию, включая `Tests/`, `scripts/`, `tools/`, `Sources/Mobile/shared-sources.txt` и `Fluid.xcodeproj`.

## Метод

1. Инвентаризация расхождения: `git diff --numstat upstream/main origin/main`, разбивка на новые файлы, изменённые upstream-файлы, пробельные правки и сквозные темы.
2. Карта горячих точек слияния: наш объём правок в upstream-файле, умноженный на объём правок upstream в том же файле с 1.6.11.
3. Семь независимых ревью только на чтение: бэкенд встреч, сессия и конвейер встреч, ASR и текстовые провайдеры, хранение/аккаунт/публикация/приватность, desktop UI/бренд/локализация, мобильное приложение, тесты/инструменты/документация. Каждое утверждение о мёртвом коде требовало поиска по всему репозиторию, включая строковые ссылки и standalone-пробы, которые читают исходники по текстовым маркерам.
4. Проверка изменений: повторный поиск ссылок на новом `main`, синтаксический разбор всех Swift-файлов tree-sitter (991 из 1 044 файлов разбираются без ошибок до изменений, у остальных 53 ограничения грамматики; новых ошибок нет), `bash scripts/dev/check.sh`, независимое автоматическое ревью итоговых коммитов.

Ограничение: в облачном окружении нет Xcode, поэтому сборка macOS/iOS и запуск XCTest/standalone-проб не выполнялись. Всё, что нужно прогнать на Mac, перечислено в разделе «Проверка на Mac».

## Главный вывод

Мёртвого кода в новых downstream-файлах почти нет: сканирование всех объявлений нашло лишь 13 объявлений, на которые ссылаются только тесты, и все они осознанные тестовые точки входа. Новые возможности в основном подключены через правильные upstream-контракты: `TranscriptionProvider`, `MeetingTranscriptionBackendRegistry`, `PrivateAIProviderFeatureProviding`, `MeetingCaptureControlling`. Стоимость сидит не в объёме функций, а в способе интеграции:

1. **Upstream-код переносится в новые файлы.** Чтобы файл компилировался для iOS, для CLI `fv-serve` или для standalone-пробы, upstream-объявления вырезались в отдельные файлы. После этого каждая правка upstream в этих объявлениях превращается в ручной перенос. Пример из реальной истории: при синхронизации 1.6.13-beta.2 изменение списков языков Parakeet пришлось вручную перенести в `SettingsStoreSpeechModels.swift`. Таких файлов найдено больше десяти.
2. **Сквозные темы протянуты руками через upstream-файлы.** Язык интерфейса (`PichiLocalization`): 115 upstream-файлов, 1 381 добавленная строка. Бренд (`AppBrand`, `BrandPackage`): 83 файла, 315 строк. Приватный профиль: 70 файлов, 638 строк. Только 81 из 267 изменённых upstream Swift-файлов затронут без этих тем.
3. **Параллельная тестовая система.** Около 53 тыс. строк standalone-проб компилируют отдельные исходники через `swiftc`, многие режут Swift-код по текстовым маркерам (422 якоря указывают в файлы, которыми владеет upstream). Эти пробы не запускаются в CI, а их маркеры фиксируют расположение кода: из-за них код выносился в отдельные файлы и не мог вернуться. Один такой непривязанный тест уже падает на `main` (см. «Найдено попутно»).
4. **Наслоение исправлений.** Повторные одинаковые проверки подряд, лестницы перегрузок с пересылающими значениями по умолчанию, растущие наборы флагов совместимости, диагностика в релизной сборке, вручную добавляемые ключи String Catalog (все 3 758 записей имеют состояние `manual`, около 250 не имеют статических ссылок).
5. **Дублирование «трубопровода» между похожими функциями.** Три установщика закреплённых артефактов, пять копий слота «замороженной» конфигурации в провайдерах, четыре хелпера Keychain, пять HTTP-клиентов, два парсера `Retry-After`, три проекции приватного состояния в UI.

Принцип наименьших изменений здесь означает: оставлять upstream-код на его месте и в его виде, а новое поведение подключать через одну точку расширения на функцию.

## Выводы по подсистемам

### Бэкенд транскрипции встреч

Скелет upstream (реестр, контракт бэкенда, одна фабрика runtime на запрос, сборщик транскрипта) расширен правильно, модель-специфичных фабрик в общем коде нет. Проблемы:

- **Мёртвый путь идентификации спикеров по окнам PCM** (около 150 строк): атрибуция теперь делается один раз после остановки, но `MeetingPCMIdentityState`, ветка спикеров в `pcmUnits`, `identityLinks` и `pcmAdmission` остались, а upstream-функция `links()` при этом переписана. Удалить и вернуть тело `links()` из upstream.
- **Механизм ограничений PCM-допуска по устройству без единой регистрации** (около 115 строк в upstream-файле `MeetingTranscriptionBackend.swift`, плюс конвейер, строка каталога и тесты). Удалить; вернуть, когда появится измеренное ограничение.
- **Повторная валидация** одного и того же правила на каждом слое; в этом PR убраны доказуемо пустые повторы, остальное требует одной точки входа на фазу.
- **Растущие флаги совместимости:** восемь отпечатков рецептов владельца голоса и восемь булевых флагов политики атрибуции. Заменить таблицей «отпечаток → рецепт», сохранив сами отпечатки.
- **Около 2 000 строк downstream-типов внутри upstream-файлов** (`MeetingProductionParakeetNemotronRuntime.swift`, 813 строк в конце `MeetingLiveModels.swift`). Переносить вместе с правкой проб, которые режут эти файлы по комментариям.
- Вендорный `Nemotron3/` (1 894 строки, Apache-2.0) нужен, пока закреплённый FluidAudio не содержит этот runtime. Неиспользуемый API в нём оставлен намеренно: вендорный код должен совпадать с источником до замены зависимостью.

### Сессия, захват, конвейер и сводки встреч

- **Grounded-сводки не дублируют upstream-шаблоны:** это другой продукт (map-reduce с JSON-схемой и ссылками на реплики). Дублируется обвязка: запись sidecar-файлов (три копии), обновление при смене профиля, запрос к Ollama `/api/chat` (повтор `OllamaChatAdapter`).
- **Допуск записи встроен в `performStartRecording`:** тело выросло примерно с 250 до 500 строк, 15 статических вызовов `PichiMeetingProviderFactory`, проверка «выбор не изменился» повторена 7 раз. Нужен один контракт `admitRecording` у внедряемого `MeetingProcessingControlling`.
- **Лестницы перегрузок** с пересылающими значениями по умолчанию (`prepareMemoryAudio` с четырьмя требованиями при одном вызывающем, `delete` трижды в `MeetingSessionStoring`); у тестовых реализаций предикат PCM-маршрута уже разошёлся с продакшен-реализацией.
- **Переиндентация upstream-кода:** в `MeetingCaptureEngine.start()` 221 строка диффа только пробельная из-за обёртки `do/catch`. Вынести тело в приватную функцию с исходными отступами.
- Три уровня трассировки поверх upstream `AudioTopologyDiagnostics`, восемь upstream-блоков `#if DEBUG` превращены в `#if DEBUG && os(macOS)`. Достаточно iOS-заглушки `AudioTopologyDiagnostics`.

### ASR и текстовые провайдеры

- **`Vendor/TranscribeCpp`** (2 957 строк) копирует upstream-пакет `transcribe-cpp-swift` 0.1.2 ради около 120 строк API `runWhisper`. Единственный потребитель: порог качества Whisper Tiny для коротких записей и логирование. Путь наименьших изменений: предложить эту привязку в upstream-пакет (те же сопровождающие), вернуться к удалённой зависимости и удалить вендорную копию.
- **Копии одного и того же:** слот «замороженной» конфигурации захвата в пяти провайдерах; конвейер «скачать, проверить, атомарно подменить» в трёх хранилищах артефактов, хотя upstream уже имеет `ParakeetArchiveInstaller.swap`; классификация конечной точки размазана по `LLMClient` в 15 ветках.
- **`FileTranscriptionService.transcribeFile`:** 314 из 630 строк диффа только пробельные из-за обёртки тела в замыкание. Использовать уже применяемый в проекте приём `…Bound`.
- Политика резидентности Ollama (держать модель загруженной) противоположна upstream-политике выгрузки по простою. Нужно продуктовое решение.

### Хранение, аккаунт, публикация, приватность

- Возврат `Keys` и разбор «склада» `SettingsStoreMeetingPreferences.swift` (около 300 из 354 строк перенесены из шести мест upstream). План ниже.
- Одно имя уведомления `"SettingsStore.privateProfileWillChange"` объявлено дважды и отправляется дважды за переход.
- `PrivateProfileStorage.isReadable(_:)` существует, но 15 копий выражения остались инлайном (12 в upstream-файлах); в этом PR заменены две.
- Четыре хелпера одиночной записи Keychain с разошедшимся маппингом ошибок, пять HTTP-клиентов с одинаковыми делегатом и сессией, два одинаковых парсера `Retry-After`, опрос раз в 20 мс в `PichiCloudPublicationActivation` там, где можно подписаться.
- «Legacy»-вход не мёртвый: это текущий вход Pichi; OIDC никуда не сконфигурирован. Выбор между ними продуктовый.

### Desktop UI, тема, бренд, локализация

- Шесть upstream-файлов, на типы которых никто не ссылается, были перекрашены и переведены без эффекта; **возвращены к upstream в этом PR**.
- 78 обёрток `PichiLocalization.text("литерал")` внутри SwiftUI-инициализаторов не нужны: SwiftUI сам разрешает литералы через окружение. 211 замен `.foregroundStyle(.secondary)` на токены палитры можно заменить одной иерархической установкой цвета в корне темы. Обе правки возвращают сотни строк к upstream, но требуют проверки отображения на Mac.
- Около 1 500 строк downstream-типов лежат внутри upstream-файлов (`MeetingLiveCaptionBubbles.swift`, проекции, новые шаги онбординга); два upstream-типа переименованы, чтобы освободить место для обёрток.
- `ToolbarAppearanceTrace` (186 строк) включается скрытой настройкой, которую никто не выставляет, но формирует данные при каждом вычислении `body`.
- `PichiLocalization` частично повторяет выбор локализации Foundation; оценить `LocalizedStringResource` за тем же фасадом.

### Мобильное приложение

- Ядро общее: iOS использует те же координатор, конвейер, реестр, хранилища и `MeetingCaptureControlling`; параллельного конвейера нет. Это хорошо.
- В upstream-файлы добавлено 53 платформенные директивы в 17 файлах, включая 423-строчную UIKit-таблицу в `MeetingLiveCaptionBubbles.swift`. Её можно вынести в отдельный iOS-файл.
- Политика облачных действий и копия ошибок аккаунта продублированы между desktop и mobile и уже разошлись; снимок конфигурации захвата тоже строится дважды с разным запасным языком.
- В десяти UI-тестах скопирован помощник скриншотов, в интеграционных тестах по шесть одинаковых заглушек.

### Тесты, инструменты, документация

- Сама техника standalone-проб пришла из upstream, но пропорции перевёрнуты: downstream-слой (около 53 тыс. строк) больше наших XCTest-добавлений (около 29,5 тыс.). Извлечение исходников реализовано заново 23 раза, 10 драйверов вне реестра, 5 из них никем не вызываются.
- В upstream-раннеры подсажены downstream-кейсы (`run_command_model_catalog_tests.sh` вырос с 22 до 335 строк).
- 34 из 59 документов в `docs/development` не имеют входящих ссылок; шесть датированных журналов доказательств и скриншоты к ним лучше держать в описании PR или локальном хранилище.
- `.gitignore` по умолчанию запрещает `docs/` и `scripts/` и разрешает файлы по одному; список уже разошёлся с отслеживаемыми файлами.

## Правила, чтобы форк не разрастался снова

1. **Upstream-объявления остаются там, где их держит upstream.** Не выносить upstream-тип или член в новый файл ради iOS, `fv-serve` или пробы; закрывать платформенные члены на месте через `#if os(macOS)`.
2. **Новое поведение входит через шов, а не через правки по всему upstream.** Одна регистрация, одно соответствие протоколу или один файл расширения на функцию. Если функции нужно больше нескольких upstream-файлов, сначала описать шов.
3. **Один механизм на тему.** Язык через String Catalog и один помощник; имя продукта через одну подстановку; область приватного профиля через один резолвер. Не добавлять второй вариант помощника ради одного места вызова.
4. **Тесты живут в XCTest.** Не добавлять новые `Tests/run_*.sh`, компилирующие отдельные исходники, и никогда не проверять текст исходного кода (маркеры, комментарии, раскладку).
5. **Удалять вместо того, чтобы обкладывать.** Если исправление заменяет подход, старый путь удаляется в том же PR. Новый флаг, обёртка или повтор требует фразы, почему нельзя изменить прежний.
6. **Доказательства не документация.** Прогоны, скриншоты, тайминги и журналы проверок идут в описание PR или игнорируемое локальное хранилище; `docs/development/` хранит долговечные документы и по одному отчёту на синхронизацию.
7. **Общее отдавать в upstream.** Слой локализации, небольшие API в `transcribe-cpp-swift`, исправления общих ошибок (например, переписанный `TerminalService` чинит реальные upstream-дефекты). Каждое принятое изменение навсегда убирает часть диффа.

## Независимое ревью

Итоговые коммиты кода проверены отдельным автоматическим ревьюером на `d1aac203` (последний коммит с документами не меняет код). Блокеров нет, все девять коммитов кода признаны безопасными для macOS и iOS: баланс `#if` и набор объявлений `SettingsStore.swift` сверены отдельным препроцессором для обеих платформ, `update-mobile-project.py --check` проходит на каждом коммите, изменённая проба смоделирована и даёт тот же Swift-код. Уточнения по итогам ревью:

- Сообщение коммита про `MeetingAudioRetentionPolicy` неточно: `fv-serve` компилирует `MeetingModels.swift`, но раньше не компилировал отдельный файл enum, теперь компилирует и его. Это безопасно: enum зависит только от Foundation и нигде не объявлен повторно.
- `ParakeetArchiveInstaller.sha256(of:)` проверяет отмену перед каждым чтением, а удалённая копия в `WhisperProvider` проверяла после чтения. Если задачу отменят во время последнего блока, отпечаток теперь завершится `CancellationError`, а не значением. Вызов идёт внутри `runBlocking` сразу после `checkCancellation()`, формат результата прежний.
- Удалённые `DictionaryLexicalEvidenceTests` и `PhysicalProductionObservationScheduleTests` никем не запускались, но проверяли живой код. Предмет первого покрыт `PichiGigaAMIntegrationTests`; для `PhysicalProductionObservationSchedule` нужен XCTest в рамках пункта 4 плана.
