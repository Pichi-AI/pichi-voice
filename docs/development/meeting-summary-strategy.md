# Grounded meeting summaries

The public summary runtime extends the existing meeting and text-provider contracts. It uses one frozen transcript, provider configuration and execution profile for extraction, reconciliation, repair and recap reduction. No model-specific coordinator or separate small-model pipeline is required.

## Selected approach

1. Process bounded transcript windows sequentially. Extract atomic recap claims, explicit decisions, requested work, questions, corrections and answers with source indices. The application resolves those indices to immutable literal excerpts; the model does not receive persistence UUIDs or need to retype source quotations. Its source view retains each numeric choice, exact excerpt, speaker and time; the app alone restores the UUID. Default evidence choices retain up to 400 characters within the existing 500-character citation limit, keeping more local task context together while reducing repeated source metadata. The transcript-window and 128-source admission bounds remain unchanged.
2. After a structurally valid extraction, perform one separate source-first revision through the same completion contract. Read every original excerpt, recover omitted explicit requests, and correct or remove candidate claims whose exact selected excerpt does not support their actor, number, time, negation, status or uncertainty. Readiness questions and historical complaints do not assign remedial work. Return the complete corrected document in the existing schema, rather than a patch. Keep questions, proposals and opinions distinguishable from answers, commitments and established facts. An explicitly addressed request may have an owner without being accepted work; its text must preserve that distinction. Copy action owners and deadlines verbatim when supported, otherwise use null. Prompt examples must not seed actual names or dates. Recap reduction remains separate and produces coherent paragraphs without replacing the task ledgers.
3. Validate structure, source membership, literal quotations and owner/deadline support against the selected excerpts, not uncited text elsewhere in their parent turn. Source speaker labels can support owners only, never deadlines; a value cannot be joined from unrelated citation boundaries. Use at most one targeted regeneration for a validation issue. Transport failure, cancellation and unsupported output are not accepted summaries. Citation existence and literal owner/deadline support are not semantic entailment: this validation cannot prove that every paraphrase or assignment is faithful.
4. Reconcile earlier ledgers against later explicit cancellation, replacement and answers. The same existing task ledger also checks later acceptance and completion, with a typed status update and strictly later witnesses. Validate the complete batch before committing any update: every selected excerpt and its change event must be strictly later than the candidate's last source time; equal-time evidence is invalid. For structural, source or temporal rejection, permit one targeted regeneration of the complete updates array against the exact same candidate state, source catalog, indexes and frozen configuration. Both responses pass the same checks, including the combined 16-citation item limit without clipping original evidence. A second invalid response rejects the entire attempt; valid prefixes are never committed. Explicit empty updates may leave uncertain candidates unchanged, but the application never silently substitutes an empty array after failure. Transport failure, cancellation and output exhaustion never start this regeneration. Preserve earlier entries and their source history, marking the earlier state historical rather than showing two simultaneous current commitments. Reduce recap repetition separately, without replacing the action and decision ledgers with repeatedly compressed prose.
5. Retain the previous saved summary when regeneration fails or is cancelled. Keep processing alive across screen navigation, and reattach the active meeting and cancellation control when the user returns.

Recap reduction has a narrower stage contract than extraction. The existing `reducing` operation selects a recap-only schema: `summary` contains 1 to 8 grounded items and `decisions`, `actions`, `openQuestions`, `changes` and `answers` have `maxItems: 0`. Those ledgers were already independently extracted and reconciled and are retained by the application. Runtime guards reject nonempty unused arrays before citation hydration or owner validation, even if an endpoint ignores the schema. Nothing is silently cleared, stripped or salvaged. A rejected recap may use the existing single structural regeneration with identical input/schema and the same token, request and attempt budgets; a second invalid output, transport failure, cancellation or output exhaustion rejects the operation. Regular extraction and ledger schemas remain unchanged. Passing this contract does not prove that the remaining recap paraphrases are semantically faithful.

Ledger requests also carry `allowedSourceIndexes` for each candidate. The application derives those request-local choices from immutable source times and matching change/answer evidence, requiring both the selected excerpt and its event to be strictly later than the candidate's last source. The existing structured-output schema binds each candidate index to its own allowed evidence enum through nested `anyOf` branches; the root remains an object and task status stays typed. A source may be legal for an earlier candidate and forbidden for a later one in the same batch. A candidate with no possible legal witness in that event batch is omitted from that request only; its original item is preserved and reconsidered for subsequent event batches. This is not clipping a model response, deleting a ledger item or manufacturing an empty fallback. Raw APIs that ignore schema still pass the complete unchanged temporal/event/citation checks and the explicit candidate scope.

Candidate batches retain the existing 6000-character bound and also bound every schema enum occurrence to 1000, including global source definitions, branch candidate indexes, scoped witnesses and task status choices. This uses the shared [structured-output JSON Schema subset](https://developers.openai.com/api/docs/guides/structured-outputs), where nested `anyOf` is permitted but a root union is not. [Local Ollama structured output](https://docs.ollama.com/capabilities/structured-outputs) uses the same schema contract. These constraints do not determine whether an answer semantically resolves a question; that still requires faithful model output and independent review. No provider/model-name condition or additional retry budget is introduced.

The revision keeps every original source choice and any additional valid short literal excerpts selected by a compatible API. Deduplication never clips evidence or changes the 128-source, 64 KB input or per-item evidence limits. Candidates use the same request-local source indices; persistence UUIDs remain application-owned. A failed, truncated or cancelled revision rejects the entire attempt without publishing the earlier extraction as a fallback. This adds one sequential request per extracted window within the existing shared request, token and time budgets. It is model-assisted correction, not a deterministic proof of entailment or a measured quality improvement.

This follows the locate-then-summarize direction of [QMSum](https://arxiv.org/abs/2104.05938), the error-specific feedback approach in [What's Wrong? Refining Meeting Summaries with LLM Feedback](https://aclanthology.org/2025.coling-main.143/) and staged meeting-summary composition studied by [Dialpad](https://arxiv.org/abs/2310.19233). These papers motivate implementation choices; they do not certify this application's models or Russian summary quality. The existing canonical document, validation and meeting resource ownership remain the extension boundaries.

## Structured tasks and presentation

The existing action item keeps its `text`, `owner`, literal `deadline` and `evidence`. Three optional fields extend that same value type: `title` names the action, typed `status` distinguishes requested/proposed/agreed/completed/cancelled, and typed `urgency` distinguishes urgent/normal/unspecified. No existing domain enum represents these meeting semantics, so these two small enums describe output data rather than a new provider or processing abstraction. Fresh generation requires all three fields even when an API ignores its JSON schema. Saved legacy documents use their separate decoder/validation path and still render; they never acquire an implicit agreed state. Partial metadata, unknown enum values and task metadata on other item categories are rejected. The existing task ledger requires an explicit update-status field (including JSON null for an unclassified replacement), restricts changes to later cited sources, and retains earlier tasks as historical. A completed earlier task is labelled completed later rather than cancelled; presentation does not advertise its former status as a current commitment.

The shared summary view displays the task title, description, status, urgency, owner, literal deadline and source disclosure using its existing typography/theme roles. `copyMarkdown` assembles headings and metadata from structured values and original source times. It escapes data punctuation so source/model fields cannot create HTML or links. The old plain `copyText` contract remains available for existing callers. UI labels are localized through String Catalogs; user task titles, descriptions, names, dates and source speech remain data. Structural validation and typed states cannot prove semantic acceptance or urgency; those still require source review and model evaluation.

## Thinking and resource ownership

The ordinary profile permits 8192 context tokens, 3000 generated tokens, 180 seconds per request and 600 seconds per whole attempt. Extended processing permits 16384 context tokens, 8192 generated tokens, 900 seconds per request and 3600 seconds per whole attempt. Thinking uses the selected model's existing shared reasoning settings. Extended time does not automatically enable it, and a boolean thinking control must not be advertised as an unsupported maximum effort level. See [Ollama thinking controls](https://docs.ollama.com/capabilities/thinking).

The generation token limit includes reasoning and the final answer. A completed transport response with `done_reason: length` is output exhaustion, even when thinking consumed the available tokens before a complete final object. It remains a rejected attempt and can occur on short inputs. The localized output-limit diagnosis suggests disabling thinking or choosing the extended processing budget; it is distinct from invalid structured output and does not imply that the selected model must be replaced. All extraction, source-first revision, structural regeneration, ledger regeneration and recap requests consume the same 256-completion operation limit and whole-attempt deadline; no stage resets them. Resource settings and cache identity are fixed when an attempt starts; changing preferences during it cannot retarget its requests.

Native Ollama attempts create an owned, unpredictable alias of the admitted model artifact, verify its digest and use that alias for every request. Only the owned alias is deleted. The logical model identifier remains visible in the UI; the artifact digest is included in saved provenance and cache identity. Other API transports keep their existing server contracts rather than pretending to support local artifact pinning.

Cancellation and the total deadline join client work and release before admission and ASR resources are restored. Release failures remain visible after cancellation and prevent publication. There is a server-side limit: an Ollama copy may finish after its HTTP timeout and after a DELETE returned 404. Bounded client cleanup cannot guarantee absence of that late alias. It does not enumerate and delete other installations' models or force a global runner unload.

Offline viewing can show a validated saved summary matched to the transcript and base configuration. It is explicitly labelled historical because the current model artifact could not be checked. A reachable changed digest invalidates that cache.

## Evidence before changing defaults

A private October 10 experiment exercised Qwen3.5 0.8B, 2B, 4B and Gemma 4 E2B on one complete hour-long Russian transcript. Each model received two frozen prompts with thinking both disabled and enabled, for 16 direct prose attempts. The matched off/on pairs used the same artifact, source, family sampling, seed, 65536 context and 32768 generation limit. Every attempt completed and cleanup was joined. All 16 outputs had a critical semantic distortion in independent blinded review.

For Qwen3.5 4B, thinking reduced weighted reference fact coverage from 42.5% to 33.0% with the original prompt, and from 37.7% to 28.3% with the engineered prompt. Time rose from 44 to 109 seconds and from 42 to 130 seconds respectively. This is one sample per cell, not a universal model ranking. Coverage is not accuracy. It does not justify making thinking or a particular model an automatic default.

A separate native structured slice on four synthetic summary cases accepted two of four standard attempts and one of four extended-thinking attempts. The other extended attempts exhausted their output budget. Structural acceptance is separate from independent semantic quality. The direct prose experiment has different prompts and serving parameters; do not merge its success counts with native compatibility results.

Keep the full summaries, independent annotations, request hashes, memory observations and private sources in ignored local evaluation storage. The observed machine had 128 GiB of memory. Server/runner RSS is neither unique physical memory nor proof of operation on an 8 or 16 GB Mac. Only a complete corpus with no critical semantic failures and repeated finalist cases qualifies a default recommendation under the [evaluation protocol](text-model-evals.md).

Run `bash Tests/run_meeting_summary_evidence_tests.sh` for standalone synthetic checks of the production evidence/value-type code. The full native suite also covers generation, repair, reduction and resource ownership. Prompt refinements and larger evidence choices need separate real-model semantic evaluation; passing these checks does not establish a higher model score.
